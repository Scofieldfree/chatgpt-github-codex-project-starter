# ChatGPT ↔ GitHub ↔ Codex / Work 协作流程

本文件只解释协作流程如何运转；所有规则以根目录 `AGENTS.md` 为唯一权威，冲突时以 `AGENTS.md` 为准。

## 核心角色

| 角色 | 主要职责 | 不应承担的职责 |
| --- | --- | --- |
| 用户 | 定目标、做关键取舍、授权外部动作、接受结果 | 手工搬运所有上下文 |
| ChatGPT | 探索、澄清、方案比较、决策沉淀、Task 设计、Review | 在信息不足时假装结论稳定 |
| GitHub 仓库 | 保存当前项目事实、代码、历史和协作记录 | 代替真实运行验证 |
| Task | 固定单次工作的范围、验收与验证方式 | 承载整个项目的全部背景 |
| Codex / Work | 检查仓库、实现、测试、运行、修复和汇报 | 自行改变产品方向或静默扩展范围 |
| PR / Diff | 展示可 Review 的实际变更 | 仅凭描述证明行为正确 |

## 完整闭环

```text
                  ┌──────────────────────────┐
                  │ ChatGPT：探索与方案比较 │
                  └────────────┬─────────────┘
                               │ 用户确认
                               ▼
                  ┌──────────────────────────┐
                  │ Settled Decisions        │
                  └────────────┬─────────────┘
                               │ 写入对应位置
                               ▼
                  ┌──────────────────────────┐
                  │ GitHub：项目长期事实     │
                  └────────────┬─────────────┘
                               │ 创建小型 Task
                               ▼
                  ┌──────────────────────────┐
                  │ Codex / Work：执行       │
                  └────────────┬─────────────┘
                               │ 代码 + 证据
                               ▼
                  ┌──────────────────────────┐
                  │ Review：Diff + Verification│
                  └───────┬──────────┬───────┘
                          │通过      │不通过
                          ▼          ▼
                       Merge      Fix Task
                          │          │
                          └────┬─────┘
                               ▼
                         Next Iteration
```

## 阶段 0：仓库初始化

### 输入

- 一句话项目想法
- 已有仓库或新仓库
- 本项目骨架

### 动作

1. 复制并重命名整个项目骨架。
2. 在现有 `AGENTS.md`、`README.md`、`docs/` 和 `tasks/` 中填写已经确认的内容；未知内容写 `TBD`。
3. 定义最小验证方式和基础仓库命令。
4. 初始化 Git 并提交第一版文档，让后续所有 Agent 都能读取。

### 出口条件

- AI 知道应该先读什么和如何验证
- 产品目标与 MVP 边界至少有第一版
- 当前未知项没有被伪装成决定

## 阶段 1：探索与澄清

### ChatGPT 应做

- 识别用户、问题、使用情景和期望结果
- 区分事实、假设和偏好
- 找出会显著影响 Scope 或 Architecture 的关键问题
- 只比较真正相关的方案，并说明代价
- 把仍未确认的内容留在 Exploration 状态

### 不应做

- 直接生成大而全的 PRD、架构和几十个任务
- 把顺口提到的想法写成 P0
- 在没有仓库证据时断言现有实现方式

### 出口条件

- 目标问题和用户价值清楚
- MVP 与 Non-goals 基本清楚
- 最大风险和待验证假设被识别

## 阶段 2：稳定决策与文档沉淀

各类信息的唯一权威位置以 `AGENTS.md` 第 5 节为准，更新触发条件以 `AGENTS.md` 第 7 节为准，此处不重复路由表。

更新时同时检查：

- 是否与代码或其他文档冲突
- 是否重复保存同一事实
- 是否需要给旧决定标记 `Superseded`
- 是否能通过链接代替复制

### 出口条件

- 当前有效结论已经可被新会话恢复
- 重要取舍不仅有结果，还有原因与重审条件

## 阶段 3：Task 设计

生成门槛、状态机、编号和分支约定以 `AGENTS.md` 第 8、9 节为准。设计时，一个合格 Task 应能回答：

1. 为什么要做？
2. 这一次必须产生什么可观察结果？
3. 可以修改哪些范围？
4. 明确不做什么？
5. 必须遵守哪些架构和兼容性约束？
6. 怎样判定 PASS / FAIL？
7. 执行哪些验证并留下什么证据？

### 拆分信号

出现以下任一情况时，考虑拆分 Task：

- 包含多个可独立交付的用户结果
- Acceptance Criteria 超过一组互不相关的行为
- 需要同时改变多个架构层且无法独立验证
- 预计长时间处于“部分完成”状态
- Non-goals 很难说清

### 出口条件

- 执行者不需要猜测产品方向
- 失败时能清楚指出是哪条标准未满足
- 验证步骤可在当前环境实际运行

## 阶段 4：Codex / Work 执行

### 推荐顺序

1. 读取 `AGENTS.md`、当前 Task 和相关文档。
2. 检查实际代码、测试和工作区状态。
3. 给出简短实施计划，确认工作不越界。
4. 做最小必要变更。
5. 运行静态检查和目标测试。
6. 按 Task 运行真实行为验证。
7. 修复本次范围内的失败。
8. 汇报变更、验证证据、限制和 Follow-ups。

### 执行报告最少包含

- 完成了什么
- 修改了哪些关键文件或模块
- 每条 Acceptance Criterion 的结果
- 实际运行的验证与结果
- 未解决问题、风险和未执行的验证
- 是否更新了文档以及原因

## 阶段 5：Review 与合并

Review 顺序建议：

1. 先读 Task，恢复目标与边界。
2. 看 Diff，确认实际变更而非执行摘要。
3. 逐条核对 Acceptance Criteria。
4. 检查 Architecture 和 Decision 一致性。
5. 检查测试是否验证了行为，而不仅是实现细节。
6. 查看真实运行证据和遗漏验证。
7. 判断文档是否需要同步。

### Review 结果

- `PASS`：满足标准，可以合并
- `PASS WITH FOLLOW-UP`：当前任务满足，另建非阻塞 Task
- `FIX REQUIRED`：存在范围内缺陷，继续当前 Task
- `RE-SCOPE`：需求或架构前提已经变化，回到讨论与文档阶段

## 阶段 6：迭代与清理

合并后：

- 更新 Task 状态或保留 PR 链接
- 只在事实变化时更新长期文档
- 把新发现但未纳入范围的问题创建为候选 Task
- 检查当前 Roadmap Phase 的 Exit Criteria
- 下一轮仍从最小完整结果开始

## 常用对话指令

### 继续探索

```text
先保持 Exploration。请比较这几个方案，但不要更新正式文档或创建 Task。
```

### 沉淀决定

```text
把刚才已确认的决定写入对应仓库文档。不要收录未确认想法；列出修改位置与原因。
```

### 生成 Task

```text
基于当前仓库事实，为下一项最小可验证工作创建一个 Task。明确 Non-goals、PASS / FAIL 标准和真实验证步骤。
```

### Review Codex 结果

```text
请先读 Task、相关文档和实际 Diff，再按 Acceptance Criteria Review。不要只依赖执行摘要；区分阻塞问题与 Follow-up。
```

## 失败模式与修正

| 失败模式 | 修正方式 |
| --- | --- |
| 对话很长但没有稳定结论 | 明确 Exploration / Decision，生成短决策摘要 |
| 每次都重新解释项目 | 把当前事实写入 GitHub 文档并建立阅读顺序 |
| Task 越做越大 | 强化 Non-goals，把发现项转为 Follow-up |
| 文档互相矛盾 | 为每类事实指定唯一权威文件，删除重复 |
| Codex 说完成但产品不可用 | 把真实用户路径写进 Verification |
| 为未来过度设计 | 写明 Revisit When，当前选择最小可替换方案 |
| 文档与代码漂移 | Review 时比较文档、Diff 和运行行为，更新错误的一方 |
